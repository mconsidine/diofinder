# Audit — speed, wedging/races, workflow integrity (v0.11.23, July 2026)

Three-lens review of the tree at v0.11.23 (`1d0b483`): (1) concurrency /
wedging / race conditions, (2) hot-path performance on the Pi Zero 2 W,
(3) workflow integrity (state machines, atomicity, silent degradation).
Findings were independently re-verified against the code before inclusion;
line numbers refer to v0.11.23. The open items are mirrored as prioritized
backlog tasks in `AGENTS.md` §7 (IDs below match). Sections at the end list
what was checked and found sound, so future audits don't re-tread it.

Baseline numbers used in cost estimates: frame = 960×760 u8 = 0.73 MB; one
`Manager().dict()` operation = one pickled unix-socket RPC ≈ 0.3–1 ms on the
Zero 2 W; solve cadence target = 1/exposure (0.05–1 s).

---

## 1. Wedging and race conditions

### W1 (HIGH) — A hung camera pipeline is undetectable; frozen pointing served as live

`camera_proc.py` `capture_array("main")` has no timeout; the retry path only
covers captures that **raise**. A capture that **blocks** (libcamera / CSI /
sensor-I2C stall — a known picamera2 failure mode) stops publishes silently.
`FrameSlots.acquire_read_slot` deliberately returns the *current stale frame*
on its 5 s timeout, the solver does not check whether `seq` advanced, so it
re-extracts and re-solves the identical frame every 5 s and publishes a fresh
`epoch_monotonic` — which is exactly what the watchdog watches. Net effect: a
mid-session camera hang keeps LX200/webui reporting the last solved RA/Dec as
`solved=True` indefinitely while the sky rotates away. The documented "dead
camera surfaces as a stale epoch" mechanism covers only the raising path.

**Fix direction**: the solver already holds the truth — the timeout path
returns an unchanged `seq`. Count consecutive same-seq returns; after N
(e.g. 6 = 30 s) publish `frame_stale=True` and stop refreshing
`epoch_monotonic`, so the existing watchdog converts a camera hang into a
systemd restart. (Alternative: camera heartbeat key + watchdog check.)

### W2 (HIGH) — Align (`:CM#`) queues can wedge the comms main thread; response correlation can mis-deliver

Three composing defects:

1. `comms_proc._do_alignment` does a **blocking, timeout-less**
   `align_request_q.put(req)` on the comms **main thread** (queue maxsize 4).
2. The solver drains the align queue only **after the dark-frame gate** — an
   intentional v0.11.x change (requests stay queued until a bright frame). So
   while frames are dark (capped lens, dome closed, thick cloud), requests
   are never consumed: four timed-out Syncs fill the queue and the **fifth
   `:CM#` blocks the comms main thread forever**. No LX200 client can be
   served again; the maint socket and watchdog threads stay healthy and the
   solver keeps publishing, so nothing restarts the unit.
3. `_do_alignment` accepts the first response with
   `completed_at >= req.requested_at` — there is no request identity in
   `AlignRequest`/`AlignResult`. A superseded/late result from request #1 can
   be accepted as request #2's outcome; in the worst interleaving a *success*
   computed for the **old** target is accepted and **persisted via
   `save_keys` as the boresight** for the new sync.

**Fix direction**: `put_nowait` (or `put(timeout=1)`) in both directions,
treating a full queue as "align busy" (`:CM#` reply "fail: busy"); add a
monotonically increasing `request_id` echoed in `AlignResult` and discard
non-matching responses (the pattern `_wait_for_reply` already uses).
Optionally drain-and-reject align requests on dark frames.

### W3 (HIGH, also F1) — `set_db` double-fault leaves a DB-less zombie solver the watchdog cannot see

`solver_proc` releases the old DB before loading the new one (correct for
512 MB RSS). On a failed load it reloads the previous DB — but if **that**
also fails (plausible under the same memory pressure that failed the first
load), `state.solver_t3` stays `None` with only a CRITICAL log. Every
subsequent frame raises `AttributeError` inside the solve `try`, is caught,
publishes an empty solution **with a fresh epoch** — so the watchdog never
fires and the device extracts stars but never solves until a manual restart,
logging a warning every frame. The in-code comment "the watchdog restart
reloads the configured db" describes a restart that never happens.

**Fix direction**: on double-fault, `os._exit(1)` (systemd restarts and
loads the configured DB at startup — making the comment true), or publish a
`solver_dbless` flag the watchdog enforces. Throttle the per-frame warning
either way.

### W4 (MEDIUM) — Camera RPC timeout (2 s) < camera command latency (one frame period, up to 10 s)

camera_proc drains its command queue once per loop iteration, and each
iteration blocks in `capture_array` for ~one exposure. `_call_camera`
defaults to 2 s while `exposure_s` may be 10 s. At exposures over ~2 s every
camera RPC (auto-exposure's GET_EXPOSURE, `exposure_get`, `seeing_get`'s
camera read, `dark_capture` snapshot) mostly times out: AE silently stops
adjusting, the Camera page shows "camera did not respond", late replies are
discarded as stale. The solver-side analog is marginal (5 s frame wait vs
5 s `_call_solver` timeout).

**Fix direction**: drain the camera command queue from a small helper thread
(single-mutator state) or scale the RPC timeout with current exposure
(`2 + 2×exposure_s`); bump `_call_solver` default to ~8 s.

### W5 (MEDIUM) — IMU wedged in a kernel I2C read disables bg_cache slew detection with no signal

`imu_proc` `read_i2c_block_data` can block indefinitely in the kernel (BNO055
clock-stretch wedge); the thread then never reaches the error path that
clears `imu_available`. Staleness-gated consumers are safe (`_imu_predict`,
`_imu_propagate_hint` check `imu_t` age ≤ 2 s), but the solver's bg_cache
feed gates on the **flag only**: it keeps calling `note_motion(frozen_quat)`,
so slews are never detected AND the fail-streak invalidation stays disabled
("IMU-less only"). Every slew then re-acquires against a stale STEADY
background model until the 60 s max-age expiry — for the rest of the
session, unlogged.

**Fix direction**: in solver_main, treat a stale `imu_t` as IMU-lost:
`if imu_available and now - imu_t < 2.0: note_motion(...) else:
note_imu_lost()`. One-line semantic change matching the hint path's gates.

### W6 (MEDIUM, structural) — Nothing monitors comms itself (or the camera; see W1)

The only liveness enforcement in the system is comms' watchdog thread
watching the **solver's** epoch. A wedged comms main thread (W2), a comms
thread stuck under the `save_keys` flock on a stalled filesystem, or a
camera hang (W1) are invisible: the process objects stay alive, so both the
launcher (`is_alive()` checks) and systemd (`Restart=on-failure`) are
content. **Fix direction**: `WatchdogSec=` + `sd_notify(WATCHDOG=1)` pings
from the launcher, fed by cheap end-to-end self-checks (maint-socket ping,
`FrameSlots.seq` advance). One mechanism covers W1 and W6.

### Low-severity wedging items

- **W-L1** — bg_cache generation guard publish-window race: the worker
  checks `_invalidate_gen` *before* publishing and clears `_needs_rebuild`
  *after*; a `note_camera_settings` flush landing in that microsecond window
  has its rebuild request wiped (old-pedestal model served until the 60 s
  max-age). Re-check the gen after clearing the flag.
- **W-L2** — `_call_solver` does a blocking `put` (queue maxsize 16) while
  holding `_solver_call_lock`; during a legitimate 60 s `set_db` pollers can
  fill the queue and the 17th caller freezes every solver-backed maint
  command until the drain. `put(timeout=1)` + error return removes the
  pile-up.
- **W-L3** — `dark_capture` (64 × 0.3 s ≈ 19 s + median) runs inline in the
  solver command handler **without** setting `solver_busy_t` (unlike
  `set_db`), leaving ~7 s of margin to the 30 s watchdog — negative margin
  if the user lowered `watchdog_timeout_s` on the Config page.
- **W-L4** — a second LX200 client is accepted at TCP level (backlog) but
  never served a byte until the first disconnects; invisible to the user.
  (Single-client is accepted-by-design; the *invisibility* is the finding.)
- **W-L5** — both server sockets accumulate `buf += chunk` with no length
  cap while no delimiter arrives; the LX200 port is network-exposed on a
  512 MB device. Cap at a few KB and drop.
- **W-L6** — `maint.call` default timeout 10 s < several handler runtimes
  (`seeing_set` waits up to 60 s on `set_db`); `diofinder-ctl seeing set`
  can report failure while the toggle actually completes, prompting a
  duplicate heavy reload.
- **W-L7** — `_read_current_frame` holds the read slot without try/finally
  (harmless today — writer never starves with 3 buffers — but free to fix).

## 2. Performance (Pi Zero 2 W)

Biggest combined wins: **P1+P2+P8** (solver-side IPC: ~6–13 RPCs/frame → ~2,
i.e. ~3–12 ms back per solved frame — a double-digit share of the frame
budget at short exposures) and **P3+P4+P6** (poll-path RPC collapse + binary
frame transport for CPU-0 headroom / pointing latency).

### P1 — `_imu_update_reference` fires 6–12 Manager write RPCs per successful solve

Every solve writes the atomic `imu_ref` (1 RPC) **plus** the five legacy
split keys (`imu_ref_q/ra/dec/roll/t`, kept "for webui/status display") —
5 more RPCs; a moving solve adds `imu_calib_C/quality/pairs/n`,
`imu_frame_R`, `imu_frame_quality` (6 more). ~2–12 ms per solved frame; in
TRACKING mode this bookkeeping costs more than the ROI extraction saving the
mode exists to capture. **Fix**: write only `imu_ref` per solve (have
status/webui read it), and batch the calibration keys into one composite key.

### P2 — `imu_calib_pairs` is dead payload in every snapshot

A 20-entry list of float tuples lives in shared_cfg but is only read back by
the solver itself — inflating **every** `dict(shared_cfg)` snapshot (once
per solver frame, 1–2× per LX200 poll) by ~2–4 KB of pickle, plus a write
RPC per moving solve. **Fix**: keep it as a solver-local variable.

### P3 — `:GR#`/`:GD#` poll pair costs up to 4 full-dict RPCs; the parked common case always pays the maximum

Each command snapshots `dict(shared_cfg)` (correct — 1 RPC), but when the
motion gate reports "parked" (the normal state) `_imu_predict` returns None
and the handler additionally snapshots `dict(latest_solution)`. SkySafari
polls both several times per second → 8–16 IPC ops/s on CPU 0 (which also
hosts the Manager process). **Fix**: a ~100 ms-TTL snapshot cache shared by
:GR/:GD — :GD virtually always follows :GR within milliseconds, and the α-β
filter already dedupes on `imu_t`, so ≤100 ms staleness is invisible.

### P4 — Live-view `frame_get` transport makes ~6–7 full-frame copies plus base64+JSON

Per poll (every 1250 ms): solver copy + `tobytes()` (2× 0.73 MB, inside the
solver's command drain), 0.73 MB pickle through the reply queue, comms
`b64encode` (0.97 MB, GIL-held), JSON wrap, webui 1 MB JSON parse +
`b64decode` + `frombuffer().copy()` — roughly 20–40 ms CPU + ~5 MB memory
traffic per poll on a bandwidth-bound box, plus up to one frame period of
latency (commands are serviced between frames). **Fix**: binary framing on
the maint socket (JSON header + length-prefixed raw payload) halves it; a
dedicated display SHM segment written by the solver (seq-rechecked reads)
eliminates the transport entirely.

### P5 — bg_cache median-stacks at full resolution, then bins the result away

`submit_frame` copies 0.73 MB/frame; `_build_model` runs
`np.median(np.stack(8 × 0.73 MB))` — ~100–300 ms of **GIL-held** numpy in
the solver process every ~5 s — yet every published model kind is consumed
at the **binned** detection resolution (`detect_bin=2`). Binning at submit
time (0.18 MB/frame) makes the stack, the copies, and the rebuild ~4× 
cheaper. Note the estimator changes from bin(median(stack)) to
median(bin(frames)) — statistically equivalent for the background floor, but
re-verify the MAD noise level against the calibrated sigma operating points
before shipping.

### P6 — Maint `status` issues ~15 individual `shared_cfg.get()` RPCs per call

Polled at 0.8 Hz by the home page → ~12 IPC ops/s on CPU 0. The one-line
fix is the `snap = dict(shared_cfg)` pattern the :GR handler and solver loop
already use.

### P7 — IMU thread: 40 Manager write RPCs/s, forever

2 writes (`imu_q`, `imu_t`) × 20 Hz, from the **launcher** process (see
docs-drift D2). One composite `imu = (q, t)` key halves it and makes the
pair atomic (today it can tear between the two RPCs; consumers survive via
staleness checks). Needs a reader-compat shim for mixed versions.

### P8 — `calibrator.get_fov_max_error()` does a live Manager RPC every frame while uncalibrated

Called from the per-frame `_solve_kw` build, bypassing the loop's snapshot —
~0.3–1 ms/frame during exactly the blind-acquisition phase where solve rate
matters most. Pass the snapshot in.

### P9 — TRACKING mode carries ~3 ms of fixed full-frame work per frame

Strided full-frame peak scan, full-frame `np.copyto`, hot-pixel repair, and
the bg_cache submit all run unconditionally before the ROI branch — capping
the realizable gain of the 6 ms → 1.5 ms extraction target at roughly half.
Worth revisiting only if tracking graduates from experimental: derive the
peak from the ROI results' own `peak` fields, restrict repair to the window
union (keep `submit_frame` — the cache must stay warm for fallback).

### P10 — Camera capture path: one avoidable ~1.1 MB alloc+copy per frame + 1 RPC

`capture_array("main")` allocates the full YUV420 buffer, then `np.copyto`
copies the Y-plane again into SHM; `shared_cfg.get("test_mode")` is one RPC
per frame. Runs on CPU 3 — a solver rayon core. The request API
(`capture_request()` + mapped Y-plane slice copy) skips the intermediate
array; TTL-cache the `test_mode` read.

### P11 — Dark frames publish a full `latest_solution.update` every frame

Up to 20 RPCs/s at the 0.05 s exposure floor for frames carrying no
information beyond "alive". Publish the first dark frame immediately (UI
state flip), then every Nth — the watchdog only needs the epoch inside 30 s.

### Free micro-fixes

`CACHE_COMPATIBLE_MODES` frozenset rebuilt on every `bg_cache.detect()` call
(hoist to module level); centroid axis-swap list comprehensions →
`np.asarray(raw)[:, [1, 0]]`.

## 3. Workflow integrity

### F1 (HIGH) — see W3 (`set_db` double-fault zombie).

### F2 (HIGH) — The wrong-FOV escape chain never becomes truly blind; a lens change deadlocks despite following the documented reset

The FallbackGate loose retry widens only to `fov_max_error_deg` — now
**0.3°** (tightened in v0.11.21; CLAUDE.md still said 1.0°, fixed in this
audit's PR) — around the *same committed estimate*, and
`force_recalibrate()` is reachable only from a *successful* out-of-window
retry solve. Swap the 25 mm lens for a 50 mm (13.5° → ~6.8°): every solve
fails, the ±0.3° retry also fails, `force_recalibrate` is unreachable, and
the documented reset procedure (flip `fov_calibrated: false`) doesn't help
because `fov_deg` itself still holds the old lens's committed value.
Permanent no-solve with healthy star counts. **Fix**: after N further
gate-fired failures, escalate the retry to a genuinely wide window (several
degrees); make the reset procedure/Config-page reset also restore `fov_deg`;
update the conf.default/CLAUDE.md reset text meanwhile.

### F3 (MEDIUM) — Tracking mode can flap FULL↔TRACKING at a 25 % duty cycle, invisibly

Lock-in needs only 3 consecutive solves; every tracking failure resets to
FULL with no backoff, so a systematic verify-failure (stale distortion,
wheel semantics mismatch, marginal ROI centroids) produces: 3 good FULL
solves → lock → 1 failed TRACKING frame (published as unsolved) → repeat,
forever — dropping one pointing frame in four. Crucially
`tracking_recover_fail` counts only ROI-recovery shortfalls; a verify/solve
failure while tracking is **not counted anywhere**, so `tracking_status`
looks healthy during the flap. Verify failures also feed
`fallback_gate.note_failure()` (harmless today only because interleaved
successes reset the streak). **Fix**: add a `tracking_solve_fail` counter
(surfaced in `tracking_status` + debug bundle) and a relock backoff
(e.g. double the lock-frames requirement per failed episode, capped);
consider excluding verify-only failures from the FallbackGate count.

### F4 (MEDIUM) — `seeing_set` / `auto_tune commit` / `auto_tune_apply_last` report success when persistence fails

All three catch a `save_keys` failure with only a `log.warning` and return
`ok=True` — the exact "settings saved ≠ settings in force" class §4 of
AGENTS.md records, reintroduced above the hardened `save_keys`. On an SD
card gone read-only after a power blip: the DB switches, live params apply,
UI says success; next restart silently reverts. **Fix**: add
`"persisted": false, "persist_error": ...` to the MaintResponse result and
show a webui banner. One line per site.

### F5 (MEDIUM) — Solver-raise path drops the FallbackGate retry signal

The `except` around `solve_from_centroids` calls
`fallback_gate.note_failure()` but **ignores the boolean return**; the loose
retry runs only on the NoMatch path. A failure class that *raises*
repeatedly (NaN centroid from a poisoned model, wheel API mismatch) builds
an unbounded streak with the escape hatch never firing — the self-sustaining
class the gate exists to break. **Fix**: honor the return in the except
block (centroids are in hand) or at least log the suppressed fire.

### F6 (MEDIUM) — `force_recalibrate` clears in-memory calibration even when the persist fails

Opposite policy to `_maybe_commit` (which refuses to update memory on
persist failure). Config-page Reset on a read-only SD: session runs
uncalibrated, UI says success, next restart resurrects the stale committed
FOV — "the reset did nothing". Combined with F2 this defeats the only
documented lens-change remedy. **Fix**: propagate the persist failure into
the `SOLVER_OP_CALIBRATION_RESET` reply.

### F7 (MEDIUM) — `dark_capture` fixed-point path drives the camera before the AE pause and outside the restore try/finally

The SET_EXPOSURE/SET_GAIN + settle sleep run *before* `_ae_pause()` and
*before* the `try:` whose `finally` restores. (a) The AE loop can fire
during the ~2 s settle and move gain, so the "fixed worst-case" mask is
captured at a different point than requested; (b) an exception in the setup
window leaves the camera parked at 0.9 s / gain 16. **Fix**: three-line
reorder — pause first, widen the try.

### Low-severity workflow items

- **F-L1** — hot-pixel mask stores no capture metadata (exposure / gain /
  sensor mode); the output frame is always 960×760 so the shape guard passes
  across sensor-mode changes while every index points at the wrong sky
  pixel. Save metadata; warn on mismatch; show it in `hot_pixel_status`.
- **F-L2** — solver-side dark capture doesn't chain `after_seq`: at 0.9 s
  exposure, 16 reads ≈ 5–6 unique frames — the mask's MAD statistics run on
  a third of the intended samples. The chaining plumbing already exists.
- **F-L3** — `conf_migrate` matches old values as exact strings, but
  `save_keys` writes `%.10g` (`1.0` → `"1"`), so a user-persisted old
  default escapes migration. Compare via the existing `_norm()`.
- **F-L4** — `etc/diofinder.conf.default` is missing ~10 dataclass keys
  (incl. `extractor_backend`, `auto_exposure_target_matches`,
  `auto_exposure_min_gain/max_gain/nominal_s/peak_floor`,
  `star_names_path`, `star_name_brightest/radius_deg`,
  `imu_rate_gate_dps`) — the divergence report can't diff them and users
  can't discover them. Contradicts AGENTS §2.4.
- **F-L5** — unthrottled per-frame `log.warning` on the two solver
  exception paths (extraction raise, solve raise); the NoMatch/TooFew paths
  are throttled. Several warnings/second onto the SD journal under F1/W3.
- **F-L6** — zero observability for the FallbackGate (streak / fires /
  last-fire never surfaced in `calibration_status`) and the debug bundle
  omits `tracking_status`. A dozen lines; high field-diagnostic value.
- **F-L7** — `auto_tune` sweep and `dark_capture` don't exclude each other;
  interleaved snapshot/restore is last-writer-wins.
- **F-L8** — lineage badge flaps: auto_tune override pins exposure/gain,
  AE (default on) moves them, `classify_lineage` requires exact match →
  "Tuned" silently becomes "Custom". Exclude exposure/gain when AE is on,
  or use a tolerance band.
- **F-L9** — `DIOFINDER_*` env overrides silently mask UI-persisted values
  (env applies last at load; `save_keys` writes the file anyway). Log
  active env overrides at startup; surface in `version`/`status`.
- **F-M4** — `auto_exposure_peak_floor` / `auto_exposure_nominal_s` are
  documented live-mutable but no maint/webui writer exists, and both are
  missing from conf.default. Either wire them into a params_set or fix the
  docs (the CLAUDE.md table was corrected by this audit's PR; the writer
  remains to be added).

## 4. Docs drift found and fixed in this audit's PR

- **D1** — CLAUDE.md FOV section said tolerance tightens from
  "`fov_max_error_deg` (1.0°)"; the default has been **0.3°** since
  v0.11.21.
- **D2** — CLAUDE.md's process diagram showed `imu_thread` under
  `comms_proc`; it is started by the **launcher** (`diofinder_main.py`) —
  same CPU, no GIL contention with the LX200 handler.
- **D3** — CLAUDE.md's shared_cfg table said `auto_exposure_peak_floor` is
  "Written by comms (via maint)"; no writer exists (config-only today; see
  F-M4).
- **D4** — `config.py`'s tracking comment block still said "NOT a
  verify-only fast path (olive-solve exposes no verify-only API)" — stale
  since v0.11.23's `verify_attitude` wiring.

Remaining (not fixed here, tracked in backlog): the comms_proc module
docstring's command list omits several newer commands; `seeing_set`'s error
text says "requires mode 'good' or 'bad'" while `legacy` is accepted; the
conf.default reset instructions should mention `fov_deg` (folded into F2).

## 5. Checked and found sound

**Concurrency**: FrameSlots protocol (writer can't pick the reading/latest
slot; lock held microseconds; reader crash can't starve the writer);
solver/camera RPC correlation (request-id matching + stale-reply discard
under per-target locks; worker-side `put_nowait` replies); watchdog
(arm-on-first-publish + 300 s first-publish deadline + 120 s-bounded
`solver_busy_t` skip); AE pause refcount with try/finally on both users;
atomic `imu_ref` 6-tuple write/read; `config.save_keys` (flock sidecar +
tmp/replace; no nested-lock ordering anywhere in comms); bg_cache threading
(immutable model swap, frame deque lock, worker exception containment —
modulo W-L1); camera settings epoch single-writer; auto_tune/bgrun/tune
start guards (check-and-claim under lock); webui `_safe_call` never raises,
SHM fallback unregisters from resource_tracker; launcher/systemd chain
(child death → kill all → exit 1 → restart; ExecStartPre SHM/socket
cleanup; control-group kill prevents half-dead port holders).

**Performance**: solver per-frame `snap = dict(shared_cfg)` (one RPC
replacing ~30); preallocated `frame_buf` + `np.copyto`; read slot released
before extraction; new-frame gate prevents duplicate solves; single
`latest_solution.update` per frame; bg_cache steady-state (every-4th-frame
submit, atomic model swap, cheap dispatch); comms TTL caches for solver
RPCs; webui config mtime cache, half-res JPEG at 1250 ms; camera
`buffer_count=2` + `raw=None` + binned sensor mode; CPU affinity matches the
documented plan; star-name lookup, hot-pixel repair, Kabsch fits all
verified µs–ms scale.

**Workflow**: bg_cache generation guard vs camera-settings flush (modulo
W-L1); `seeing_set` DB-switch-first atomicity (the fallible step really is
first); seeing override storage (atomic JSON, sparse keys); hot-pixel
guards (`implausibly_large` on save AND load; `MIN_THRESH_DN` floor); align
queue drain placement vs dark frames (the :CM#-on-dark-frame fix holds —
the wedge in W2 is the *overflow* behavior, not the drain placement);
`_imu_predict` gate structure and 5/6-tuple compat; `imu_frame` fit gates
and graceful revert; solver hot-path IPC discipline.
